# kenosm

API-гейтвей: настраиваешь любой AI API (upstream) + SOCKS5-прокси рядом — и получаешь endpoint, по которому запросы идут к этому API **через прокси**.

## Что это

- Создаёшь «сервис» — связку `upstream API` + `SOCKS5 proxy` (ip, порт, логин, пароль).
- Сервису присваивается `slug`.
- Получаешь endpoint: `http://<host>/proxy/<slug>/<остальной путь>`.
- Каждый запрос на этот endpoint проксируется на upstream через указанный SOCKS5-прокси.
- Ключ API нейросети и пароль прокси хранятся в базе **зашифрованными** (AES-256-GCM).

## Стек

- **Go** (single binary, нативный reverse-proxy, высокая конкурентность).
- **PostgreSQL 16** (Docker) — хранение конфигов и логов запросов.
- **chi** — роутер; **pgx** — драйвер; **goose** — миграции; **x/net/proxy** — SOCKS5.
- Ключ шифрования — `SECRET_KEY` из окружения.

## Структура

```
cmd/server/            точка входа
internal/
  config/              загрузка конфигурации из env
  crypto/              AES-256-GCM шифрование секретов
  db/                  пул соединений + миграции (goose, embed)
  model/               модели данных
  repository/          доступ к данным (services, request_logs)
  transport/           кэш SOCKS5 http.Transport'ов
  handler/             admin CRUD + gateway (reverse proxy)
  logging/             асинхронное логирование запросов
  server/              сборка роутера
```

## Запуск

```bash
# 1. поднять Postgres
make db-up          # docker compose up -d db

# 2. зависимости
make tidy

# 3. запустить (миграции применятся автоматически)
cp .env.example .env   # при желании задать SECRET_KEY
make run               # go run ./cmd/server  (или make build && ./bin/kenosm)
```

Сервис слушает `:8080` (меняется через `ADDR`).

## API

### Создать сервис

```bash
curl -X POST http://localhost:8080/api/v1/services \
  -H 'Content-Type: application/json' \
  -d '{
    "slug": "openai",
    "name": "OpenAI via proxy",
    "upstream_url": "https://api.openai.com/v1",
    "upstream_api_key": "sk-...",
    "auth_header": "Authorization",
    "auth_scheme": "Bearer",
    "proxy_host": "1.2.3.4",
    "proxy_port": 1080,
    "proxy_username": "user",
    "proxy_password": "pass"
  }'
```

Поля:
- `slug` — обязателен, `[a-z0-9-]`, уникальный.
- `upstream_url` — обязателен, `http(s)://host[/base/path]`.
- `proxy_host`, `proxy_port` — обязательны.
- `auth_header` / `auth_scheme` — по умолчанию `Authorization: Bearer <key>`.
  Для API без ключа оставь `upstream_api_key` пустым.
- `enabled` — по умолчанию `true`.

### Прочие операции

```bash
curl http://localhost:8080/api/v1/services                     # список
curl http://localhost:8080/api/v1/services/<id>                # один
curl -X PUT http://localhost:8080/api/v1/services/<id> \
  -H 'Content-Type: application/json' -d '{ "enabled": false }'  # частичное обновление
curl -X DELETE http://localhost:8080/api/v1/services/<id>      # удалить
```

### Использовать endpoint

```bash
curl http://localhost:8080/proxy/openai/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}]}'
```

Запрос уйдёт на `https://api.openai.com/v1/chat/completions` **через SOCKS5-прокси**,
с автоматически подставленным заголовком `Authorization: Bearer sk-...`.
Стриминг (SSE) поддерживается.

## Рой (multi-agent orchestration)

Несколько Gemini-эндпоинтов (каждый со своим SOCKS5-прокси) работают как рой:
получают задачу, распределяют подзадачи между собой, выполняют их параллельно и
собирают итог.

- **Агенты** — это включённые (`enabled`) сервисы из `/api/v1/services`: у каждого
  `upstream_url` = базовый URL Gemini, `upstream_api_key` = ключ, `proxy_*` = SOCKS5.
  Ключи и пароли прокси хранятся в БД зашифрованными.
- Модель воркеров задаётся через `GEMINI_MODEL` (по умолчанию `gemini-3.8-flash`),
  модель планировщика — через `ORCHESTRATOR_MODEL` (по умолчанию `gemini-3.8-flash`),
  список моделей для fallback — через `AVAILABLE_MODELS`. Отдельный агент может
  закрепить свою модель полем `model`.

Чат и режимы: в веб-интерфейсе (вкладка **Chat**) это обычный чат — можно писать
сообщения, создавать новые чаты и переключаться между ними. У каждого сообщения
есть переключатель режима:

- **Single** — отвечает/работает один агент (быстро, с полной историей диалога).
- **Swarm** — включается весь рой: планировщик получает контекст всего диалога,
  разбивает задачу на подзадачи и раздаёт агентам параллельно.

Чат через API:

```bash
curl http://localhost:8080/api/v1/chats                              # список чатов
curl -X POST http://localhost:8080/api/v1/chats                      # новый чат
curl http://localhost:8080/api/v1/chats/<id>                         # чат с сообщениями
curl -X POST http://localhost:8080/api/v1/chats/<id>/messages \
  -H 'Content-Type: application/json' \
  -d '{"text":"Привет","mode":"single"}'                             # отправить сообщение
```

Ответ на сообщение: `run_id` (прогресс — по SSE на `/api/v1/swarm/run/<run_id>/events`).

Запустить задачу (роем, напрямую):

```bash
curl -X POST http://localhost:8080/api/v1/swarm/run \
  -H 'Content-Type: application/json' \
  -d '{"task":"Create a single-page portfolio website (HTML+CSS+JS) with a dark/light toggle."}'
```

Ответ: `plan` (разбивка), `contract` (общий технический контракт), `assignments`
(модель на агента), `subtasks` (кто из агентов что сделал), `final` (итог).

Как работает: агент-планировщик сначала решает, нужен ли рой вообще. Простой или
разговорный запрос («Привет», короткий вопрос) он отвечает напрямую, без
разбивки на подзадачи и без запуска воркеров. Иначе он строит **структуру**:
конкретные подзадачи, зависимости между ними, модель для каждого агента и общий
технический контракт (точные пути файлов, ID, CSS-классы, сигнатуры). Он
старается разложить работу минимум на столько независимых подзадач, сколько есть
агентов, а если план получился слишком крупным — рой просит его разложить
детальнее ещё до старта.

Задачи выполняются **всегда параллельно**: рой держит единую очередь готовых
подзадач (work-stealing). Подзадача становится доступной сразу, как только
завершились её зависимости — **без барьера «волн»**, — и любой освободившийся
агент немедленно берёт следующую готовую подзадачу. Поэтому если один агент
закончил, пока другие ещё работают, он тут же загружается новой работой, и все
агенты остаются занятыми до конца. Если готовых подзадач не осталось, а работа
ещё не сделана (слишком последовательный план или цикл зависимостей), планировщик
**на лету перераскладывает оставшуюся работу** на более мелкие параллельные
подзадачи — так масштабируется от 3 до 50+ агентов.

Готовые шаги пишут результат в общий журнал, который читают планировщик и
остальные агенты — через него агенты передают работу друг другу и не дублируют
файлы/имена. При 429 `RESOURCE_EXHAUSTED` запрос автоматически повторяется на
более лёгкой модели (сохраняя ключ и прокси), а не падает после ретраев.

У агентов есть настоящий браузер (headless Chromium): они могут открывать любые
сайты, нажимать кнопки и ссылки, вводить текст в поля, скроллить страницу и
снимать скриншоты. Браузер работает в одной живой сессии на весь запуск, поэтому
состояние (URL, позиция прокрутки, заполненные поля) сохраняется между шагами.
Прежде чем выдать результат, агент обязан проверить свою работу: открыть
страницу, «протыкать» все кнопки и ссылки, прокрутить её — и заскринить каждый
шаг (каждый клик и каждую прокрутку скриншотится автоматически). Если на странице
есть CAPTCHA, агент читает её со скриншота и вводит ответ в поле.

Агенты могут работать и с рабочим столом: запускать программы, искать окна,
фокусировать их, делать скриншоты экрана или конкретного окна, а также вводить
текст и нажимать клавиши/сочетания (например открыть терминал, ввести команду и
заскринить результат). Поиск/фокусировка окон и скриншоты идут через `xdotool` +
скриншотер (`maim`, `scrot`, `gnome-screenshot`, `grim` или `import`), а ввод
клавиатуры — через `ydotool` (инъекция через ядро/uinput), потому что синтетические
X11-события на Wayland ненадёжны (теряются key-up, клавиши «залипают»). Перед
вводом текста агент временно переключает раскладку GNOME на английскую (и
возвращает обратно), чтобы символы не превращались в кириллицу на русской раскладке.

Зависимости: `pacman -S xdotool maim ydotool xprop`. Для ввода нужен запущенный демон
`ydotoold` (если пользователь в группе `input` и настроено правило udev для
`/dev/uinput` — `ydotoold`; иначе `sudo ydotoold -p /tmp/.ydotool_socket -P 666`).
Если `xdotool`, скриншотер или `ydotool`/демон отсутствуют — соответствующие
инструменты отключаются с предупреждением в логе.

Перемещение мыши и клики работают и на X11, и на Wayland: используется виртуальный
**абсолютный указатель** (планшет) через ядро `/dev/uinput` — композитор принимает
абсолютные `EV_ABS`-события для позиционирования курсора, в отличие от XTEST и
относительных (`REL`) событий, которые GNOME Wayland игнорирует. Если доступ к
`/dev/uinput` отсутствует, мышь откатывается на `xdotool` (только X11-сессия).
Клавиатурный ввод через `ydotool` работает и там, и там.

## Расширенная статистика и стоимость

Веб-интерфейс (вкладки **Chat** и **Stats**) показывает в реальном времени:

- **что агенты читают и пишут** — каждый вызов инструмента классифицируется как
  read (`read_file`, `browser_snapshot`, `desktop_screenshot`, …) или write
  (`write_file`, `edit_file`, `run_command`, …) и попадает в живой фид;
- **сколько тратится на API** — стоимость считается по токенам и цене модели
  (USD за 1M токенов), суммируется по модели/агенту/запуску;
- **распределение по агентам параллельно** — таймлайн запуска (вкладка **Stats**)
  показывает, какой агент и когда выполнял каждую подзадачу; пересекающиеся
  полосы — это агенты, работавшие одновременно.

Цены задаются встроенной таблицей (по имени модели: `pro` / `lite` / `flash`)
и переопределяются через `MODEL_PRICES` (JSON, USD за 1M токенов):

```bash
MODEL_PRICES='{"gemini-3.8-flash":{"input":0.15,"output":0.6,"thought":0.6}}'
```

Новые endpoint'ы:

```bash
curl http://localhost:8080/api/v1/activity?limit=100              # последняя активность (read/write/…)
curl http://localhost:8080/api/v1/activity?run_id=<id>            # активность одного запуска
curl http://localhost:8080/api/v1/runs/<id>/timeline              # таймлайн параллельного распределения
```

Поле `cost` в `/api/v1/stats` — суммарные траты (итого и в разрезе модели/агента/запуска).

## Безопасность

- Секреты (API-ключ, пароль прокси) шифруются AES-256-GCM ключом, производным от `SECRET_KEY` (SHA-256).
- В API-ответах секреты никогда не отдаются; вместо них — флаги `has_api_key` / `has_proxy_password`.
- Смена `SECRET_KEY` делает старые зашифрованные значения нечитаемыми — храни ключ надёжно.
- При заданном `KENOSM_API_KEY` все `/api/v1/*` и `/proxy/*` требуют ключ:
  заголовок `Authorization: Bearer <key>` или `X-API-Key: <key>` (SSE-стримы — параметр `?key=`).
  Пустой `KENOSM_API_KEY` оставляет сервис открытым (режим разработки).
- Число одновременных запусков роя ограничено `MAX_CONCURRENT_RUNS` (по умолчанию 1) —
  это не даёт агентам разных запусков конфликтовать за общий workspace.
- Логи прокси-запросов (`request_logs`) автоматически подчищаются старше `LOG_RETENTION_DAYS`
  (по умолчанию 30 дней; `0` отключает очистку).
